A gentle introduction

How we build Japanese Word Kitchen

A plain-language guide to the computer terms, files, and steps behind the app. You do not need to know any of these words already. This page describes the current draft approach, not decisions you have already approved.

A note about the plan: The technical specification currently suggests a simple browser app made with HTML, CSS, and JavaScript. Those are recommendations in a draft. This guide explains what they mean; it does not ask you to approve the stack or start coding now.

The big picture

An app is a set of instructions that a computer follows to do something useful. For Japanese Word Kitchen, those instructions make the restaurant screens appear, choose vocabulary cards, respond to your ratings, and remember your custom words.

In the proposed setup, your browser (the program you use to visit websites) reads the app's files and shows the result on your screen. The app runs on your own computer. It does not need an online account or a separate computer somewhere else to run.

Plan→ Write files→ Browser reads them→ App appears→ Try and improve

The main ingredients

HTML — the structure

HTML is the basic written structure of a web page. It says what things are: a heading, a button, a picture, a form, or a paragraph.

Think of it as the room layout and furniture in a restaurant. It puts the counter, menu, and table in their places.

CSS — the appearance

CSS describes how the page looks: colors, sizes, spacing, fonts, and how things rearrange on a small screen.

Think of it as paint, lighting, tablecloths, and decorations. For this app, it would help create the warm paper and cozy restaurant feeling.

JavaScript — the behavior

JavaScript is a programming language. The app uses it to react when you click **Let's Study**, flip a card, rate a word, or save a vocabulary pair.

If HTML sets up the restaurant and CSS decorates it, JavaScript is the set of instructions telling the staff what to do when a customer makes a choice.

Browser — where you see the app

Safari, Chrome, Firefox, and Edge are browsers. A browser opens web pages and can run the HTML, CSS, and JavaScript files that make this app.

File — one saved piece of the project

A file is a named item on your computer. For example, index.html could hold the page structure and styles.css could hold its appearance instructions.

Code — instructions written for a computer

Code is text written in a language the computer can follow. You and the AI agent can read and change it in VS Code; the browser uses it to run the app.

VS Code — the workshop

VS Code is an editor for opening project folders and changing files. It is where we can look at the app's instructions together. It is not the app's browser and does not, by itself, put the app online.

AI coding agent — a helper in the workshop

An AI coding agent can read project files, suggest or make changes, and help explain errors. You remain the project owner: you can ask questions, inspect changes, and decide what to keep.

Data — information the app uses

In this app, data includes dish names, ingredient lists, Japanese-English pairs, ratings, and missed words. Some data is part of the app; some is entered by the learner.

localStorage — a small browser notebook

localStorage is a browser feature that can remember small pieces of information for a website on that device. The draft proposes it for custom words and missed words.

Imagine a notebook kept in this browser on this computer. It is not an online account, and it normally will not carry your saved words to another device.

Server — a program that waits for requests

A server is a program that gives files to a browser when asked. For this local app, an optional tiny server can make opening the project in a browser more reliable. It would run on your own computer, not on a public website.

Terminal — a place to type computer commands

A terminal is a text window where you can ask your computer to run a program. The draft run command uses it to start the optional local server. We can go through that command together when it is time; you do not need to memorize it.

Python's http.server — a local file helper

Python is a programming language. It includes a small tool named http.server that can serve project files to your browser from your own computer. It is one possible way to preview this kind of app, not part of the app's learning logic.

Framework — a pre-arranged set of building pieces

A framework is a collection of prepared rules and tools that helps organize an app. React is one example. The current spec draft suggests not using one at first, to avoid extra setup while learning the core app.

Backend and database — the behind-the-scenes option

A backend is the part of an app that runs on another computer and handles requests. A database is an organized place to store information. The current draft does not include either: the small amount of learner data can stay in the browser for this proof of concept.

Deployment — putting an app on the internet

Deployment means publishing an app somewhere online so other people can visit it. It is optional for this project plan. A local app can be recorded for a demo video; publishing it online is a separate step.

Responsive design — fitting different screens

Responsive design means arranging a page so it remains readable on different screen sizes, such as a laptop and a phone. CSS can handle much of this.

This is the likely technical path from the approved idea to a working browser app. Each stage produces something we can look at or try before moving on. The flow is a plan, not work that has all happened already.

4

Run it locally

A local web server can send the files from your computer to your browser. The browser requests the page and its linked files, then displays the app. “Local” means this preview is running on your computer.

Connect a user action to a result

JavaScript listens for an action such as clicking Flip. It updates the current app data, then changes the page so the browser shows the answer, rating buttons, or earned ingredient.

event function state
6

Save what should persist

When a custom word or missed word should survive a refresh, JavaScript writes it to localStorage. On the next visit, the app reads it back and uses it to fill the screen.

data localStorage
7

Check the behavior

I try the requirement in the browser: add a word, flip a card, rate it, refresh, and review it. A test is a repeatable check that the app gives the expected result.

test acceptance criteria
8

Diagnose and adjust

If something fails, I look at the visible result and the browser's developer console, which reports JavaScript errors. I trace the issue to the relevant code, make a focused change, and check again.

debugging console

Keep a checkpoint and prepare to share

A Git commit is a named checkpoint of the project files, so we can see what changed at each verified step. At the end, we prepare the demo video and public GitHub repository; publishing a live website is a separate, optional deployment step.

A single change, traced through the computer

For example, when you rate a card “4,” the button click is an event. A JavaScript event handler receives it, updates the session's state (the app's current working information), and tells the page to show the next ingredient. If the action changes lasting information, the app also saves that data in localStorage.

Click rating 4→ JavaScript handles event→ Session data updates→ Browser redraws the view

In this example, earned ingredients are session progress; custom and missed vocabulary are the information the plan says should persist between visits. The exact save rules will be confirmed against the PRD as the app is built.

What happens when you use the app

One study session, traced from your click to what you see:

  1. You choose “Let's Study.” JavaScript responds to the click and prepares a session.
  2. The app chooses dishes and words. The app's built-in lists provide the dish and vocabulary information. Its instructions pick three different dishes and fill their card slots without repeating a word pair in that session.
  3. The browser draws the tabletop. HTML provides the page pieces, CSS styles the table, and JavaScript fills in the current dish and word.
  4. You flip and rate the word. JavaScript reveals the other language. A rating of 3 or 4 adds the next ingredient; a rating of 1 or 2 adds the word to the missed tray.
  5. The dish reveal appears. The app shows the illustration for the number of ingredients earned and a cultural fact, then continues to the next dish.
  6. The app saves the lasting information. Custom words and missed words are written to the browser's localStorage so they can be read again on this browser and device later.

These are the behaviors described in the approved PRD. The exact way the files are organized is still a technical-plan choice.

The project files

A project folder is like a box holding all the related pieces of the app. The current spec draft sketches a folder structure like this: 

project/
├── index.html          the page structure
├── styles.css          colors, layout, and visual design
├── app.js              behavior and screen updates
├── data/
│   ├── dishes.js       dish names, ingredients, and facts
│   └── vocabulary.js   the built-in word pairs
├── state/
│   ├── storage.js      read and write saved words
│   └── session.js      keep track of the current study session
└── devpost/            the planning documents and review pages

This is only a proposed map, not a set of files you need to create or understand all at once. The final structure should match the choices we agree on.

What is not in this draft

The current technical draft proposes no account, no password, no online database, and no cross-device syncing. It also does not require the app to be published on the internet before it can be tried or recorded.

Those omissions are deliberate simplifications for a small first version: the central idea is the vocabulary-to-dish experience. If any of these choices feels confusing or unsuitable, we can pause and discuss it before treating the draft as approved.
